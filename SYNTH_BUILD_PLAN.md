# Synthonos: Claude Code Build Plan

This document lives at the repo root and is read by Claude Code at the start
of every session. Everything below is written to be actionable, not
aspirational. (The project was planned under the codename Verbaliser and
renamed to Synthonos before the first commit, per the plan's own instruction.)

## 0. Four reality checks before you write a line of code

These are the things that will sink the project if you find them out in week
three instead of hour one.

**1. You cannot clone Nexus or Omnisphere. You can clone Sylenth.**
Sylenth1 is virtual analog subtractive: 4 oscillators (each up to 8 unison
voices), 2 state variable filters, 2 amp envelopes, 2 mod envelopes, 2 LFOs,
a fixed effects chain. The entire sound is generated by math. This is
clonable. Nexus is a ROMpler: it plays back a proprietary sample library
through filters and effects. Without the samples there is no Nexus sound. Not
clonable. Omnisphere is a hybrid: a 60+ GB sample core plus granular
synthesis plus a virtual analog layer. Partially clonable, but the part
people recognize is the library.

So the target architecture is Sylenth-class virtual analog, plus a wavetable
oscillator mode, which gets you into Serum/Vital territory too. Study all
three plugins for interface design and for how they name things, but only one
of them is a DSP blueprint.

**2. Audio to preset is approximation, not inversion.**
"Recreate the synth in this song" is an open research problem, and the honest
framing is: find the patch in our engine's reachable parameter space that
sounds closest to the target. If the source was a Nexus preset built from
samples, the best possible answer is a convincing impression. Scope it that
way in the UI copy too, so users are not disappointed. Call it Match, not
Clone.

**3. Audio DSP fails silently.**
This is the single biggest risk to "make no mistakes." A wrong filter
coefficient does not throw. It produces sound. Slightly wrong sound.
Aliasing, DC offset, denormal stalls, clicks at note boundaries, and phase
cancellation in unison all produce runnable code that a language model will
happily tell you is correct. The mitigation is a spectral test harness built
in Phase 0, before any synthesis code exists. See section 6.

**4. Two agents, one of which waits for the other, is just sequential work
with extra failure modes.**
Claude Code subagents do not share a context window. If agent A researches
and agent B builds, the handoff has to be a file on disk anyway. So make the
research a deliverable, not an agent, and save real parallelism for genuinely
independent surfaces. Restructured plan in section 3.

## 1. Stack

| Layer | Choice | Why |
| --- | --- | --- |
| DSP engine | TypeScript in an AudioWorkletProcessor | Runs on the audio thread, no plugin format hell, one language for engine and UI. A 16 voice subtractive synth is well within budget. |
| UI | React + TypeScript, Canvas/WebGL for scopes | Fast iteration, and the knob/panel look is easy to nail. |
| Desktop shell | Tauri | "Runs locally" as a real app. Ships a static web build, tiny binary, no Electron bloat. |
| Analysis service | Python + FastAPI, localhost only | Heavy lifting (source separation, optimization, torch) belongs off the audio thread and out of the browser. |
| NL mapping | Claude API, schema-constrained JSON output | Section 5. |
| Schema | One params.schema.json that codegens everything | Section 2. The most important architectural decision in the doc. |

The fork to consciously decide on now: if this should ever load as a
VST3/CLAP inside Ableton or FL, the engine has to be Rust or C++ (use
nih-plug). That is a real cost and a real skill detour. The recommendation is
to build the TypeScript version first and keep the DSP in pure,
framework-free, dependency-free modules with no DOM access, so a Rust port
later is a mechanical translation rather than a rewrite. That constraint is
written into CLAUDE.md so agents respect it.

## 2. The keystone: one schema, everything generated

Every parameter in the synth is defined exactly once, in `params.schema.json`:

```json
{
  "filter_cutoff": {
    "label": "Cutoff",
    "group": "Filter",
    "type": "float",
    "min": 20, "max": 20000,
    "default": 12000,
    "curve": "log",
    "unit": "Hz",
    "nl_aliases": ["brightness", "darkness", "openness", "muffled", "tone"],
    "nl_direction": "higher is brighter"
  }
}
```

From that one file, `scripts/codegen.ts` emits:

1. TypeScript types and the engine's parameter table
2. The default preset
3. The UI control manifest (a new parameter appears in the panel automatically)
4. The JSON schema handed to Claude for the natural language feature
5. The parameter bounds vector used by the audio matching optimizer
6. The preset validator

If a parameter exists in five places, agents working in parallel will drift
and you will spend your evenings debugging why the UI knob says 12000 and the
engine heard 0.6. Generate everything. The codegen drift check runs in CI and
fails the build on drift.

## 3. Agent structure

Use git worktree so parallel sessions never touch the same working directory:

```
git worktree add ../synthonos-dsp feature/dsp-engine
git worktree add ../synthonos-ui  feature/ui-shell
```

Then open a separate Claude Code session in each. Both branch off a main that
already contains the schema and the test harness.

**Phase 0: solo, no agents.** Do not parallelize the foundation. One session,
one context, one head. Repo scaffold, Vite + React + TS, Tauri init;
params.schema.json with roughly 15 to 35 parameters to start, plus the
codegen script; the offline render harness (a Node script that instantiates
the engine outside the browser, renders N seconds to a WAV, and runs
assertions on it); CLAUDE.md; CI running codegen drift check plus the audio
test suite.

**Phase 0.5: the research deliverable.** One session, one job. It produces
`docs/SYNTH_REFERENCE.md` and commits it. Not an agent that hands off in
memory. A file. It should cover: Sylenth1's exact signal flow and unison
detune behavior; Serum and Vital's wavetable and modulation matrix design;
Omnisphere's macro layer; how each one names and groups controls; standard
filter topologies (state variable, ladder, comb) with their difference
equations; anti-aliasing strategies (PolyBLEP for classic waveforms,
mipmapped wavetables); ADSR curve shapes and why linear decay sounds wrong;
the standard effects chain order and why.

Critically, it also builds `docs/SOUND_VOCABULARY.md`: a producer-slang to
parameter mapping. "Warm," "gritty," "wide," "plucky," "supersaw," "reese,"
"hollow," "glassy," "aggressive." Each term gets which parameters it moves
and in which direction. This file becomes reference context for the natural
language feature in Phase 2. It is research output that turns directly into a
product feature.

**Phase 1: two agents, genuinely parallel.** Both consume the schema. Neither
blocks the other.

- Agent DSP (`feature/dsp-engine`): oscillators, filters, envelopes, LFOs,
  voice allocation, effects. Never imports React. Never touches the DOM.
  Every module gets a spectral test.
- Agent UI (`feature/ui-shell`): the full synth panel, knobs, scopes,
  keyboard, preset browser, all bound to a stub engine that returns silence
  and echoes parameter changes. Ships completely without the real engine
  existing.

Integration is a third short session that wires the real engine in place of
the stub. If the schema discipline held, this takes an hour.

**Phase 2: two agents, parallel.** Agent NL (`feature/nl-control`): section
5. Agent MATCH (`feature/audio-match`): section 4.

**Phase 3: solo.** Polish, onboarding flow, factory preset bank, Tauri
packaging, signing.

## 4. Audio to patch: ship it in three tiers

Do not try to build tier 3 first. Each tier is independently shippable and
each one improves the next.

**Preprocessing (shared by all tiers).** Separate the stem first with Demucs,
then transcribe the melody with basic-pitch to recover notes and timings. Now
you can render your candidate patch playing the same notes as the target,
which makes the comparison meaningful. Skipping this step is the most common
reason these systems produce garbage: you end up comparing a C3 sustained pad
against an F4 pluck and optimizing toward nonsense.

**Tier 1: retrieval.** Render the entire factory preset bank across a few
notes. Extract a feature vector for each: mel spectrogram statistics, MFCCs,
spectral centroid, spectral flux, harmonic to noise ratio, attack time, decay
slope, stereo width. Nearest neighbor the target against that bank. Works on
day one, needs no training, gives the user an instant starting point.

**Tier 2: parameter search.** This is the workhorse. Take the tier 1 result
as the initial guess and optimize the parameter vector with CMA-ES or
differential evolution (`scipy.optimize.differential_evolution`, or the `cma`
package). Loss is a multi-resolution STFT distance (compare magnitude
spectrograms at FFT sizes of 512, 1024, 2048, and 4096, sum the L1
distances). Do not use raw waveform MSE; phase will dominate and the
optimizer will chase noise. Budget 30 to 90 seconds per match and stream
progress to the UI so it feels alive.

**Tier 3: learned inverse.** You have a synth, which means you have an
infinite labeled dataset. Randomly sample the parameter space, render, and
train a network that maps a mel spectrogram to a parameter vector (the
Sound2Synth / InverSynth approach). Use its output as the tier 2 initializer
rather than as the final answer: a learned model is fast but imprecise, and
search is precise but needs a good starting point. Together they beat either
alone.

One caution: parameters differ wildly in perceptual sensitivity. A 5% error
in filter cutoff is audible, a 5% error in a slow LFO rate is not. Weight the
parameter space accordingly, or better, optimize purely on the audio loss and
let the parameters land where they land.

## 5. Natural language control

Never let the model emit free text. It emits a JSON object validated against
the generated schema, and anything out of bounds is rejected, not clamped
silently.

The request carries four things:

1. The parameter schema, including nl_aliases and nl_direction
2. SOUND_VOCABULARY.md from the research phase
3. The current patch state, so relative edits work ("darker," "more
   movement," "less harsh," "same but plucky")
4. The user's text

The response returns a partial patch (only changed parameters), plus a one
line explanation in plain language, plus a suggested patch name.

Three things that make this feel magic rather than gimmicky:

- **Animate the change.** When the user types "make it darker," the cutoff
  knob visibly sweeps down. That is the whole teaching mechanism. Beginners
  learn the synth by watching it operate itself. This single detail is the
  difference between a toy and the thing this project wants to be.
- **Undo stack, always.** Every NL edit is one entry. Users need to be able
  to wander and get back.
- **Explain in their words, not yours.** "Lowered the filter cutoff and added
  a touch of reverb" teaches. "Set filter_cutoff to 800" does not.

## 6. The test harness (the "make no mistakes" section)

Built in Phase 0. Every DSP module gets tests before it is considered done;
CLAUDE.md says no DSP PR merges without them. See docs/TESTING.md for the
full explanation of each assertion.

- **Silence test.** No note playing means output is exactly 0.0. Catches
  leaking envelopes and stuck voices.
- **Aliasing test.** Sweep a sawtooth from 20 Hz to 8 kHz. FFT each frame and
  assert that energy in reflected (non-harmonic) bins stays below roughly
  -60 dBFS. This is the test that forces correct PolyBLEP or wavetable
  mipmapping. Naive oscillators fail it loudly, which is exactly what we
  want.
- **Click test.** No sample-to-sample discontinuity above a threshold at note
  on, note off, and voice steal. Catches missing envelope ramps and abrupt
  voice reassignment.
- **DC offset test.** Mean of a rendered buffer stays near zero.
- **NaN and denormal guards.** Every output sample is finite. Denormals are
  flushed to zero in filter state, or the plugin mysteriously eats CPU during
  quiet passages.
- **Filter response test.** Feed white noise, FFT the output, assert the
  cutoff knee lands within tolerance of the requested frequency and the
  resonance peak has the expected gain.
- **Real-time safety.** No allocation, no console.log, no async, no
  exceptions in the process() callback. Asserted on the source, not just at
  runtime.
- **Golden renders.** Every factory preset renders a reference WAV checked
  into the repo. Any commit that changes them fails CI until the diff is
  inspected and approved. This catches the "small refactor silently changed
  the sound of everything" class of bug, which is otherwise nearly invisible.

## 8. UI: production grade look, beginner grade logic

The tension in the brief resolves with a layered interface. Same screen,
three depths, user chooses.

- **Layer 1, the text box.** Always visible, top of the window. "Describe a
  sound." This is the front door.
- **Layer 2, eight macro knobs.** Big, labeled in human words: Brightness,
  Thickness, Movement, Attack, Space, Grit, Width, Character. Each drives a
  weighted bundle of real parameters. This is exactly how Omnisphere and most
  modern hardware make deep engines approachable, and it is the layer most
  users will live in forever.
- **Layer 3, the full panel.** Every oscillator, filter, envelope, LFO, mod
  matrix slot, and effect. Looks like Sylenth. Collapsed behind an "Advanced"
  toggle, but visible enough that users get curious.

Design details that carry disproportionate weight:

- Knobs animate whenever layer 1 or 2 moves them. Users learn the synth by
  watching.
- Hovering any control shows a plain language tooltip, generated from the
  schema.
- A live spectrum analyzer and oscilloscope. Non-negotiable for the "pro"
  feel, and it genuinely teaches people what they are hearing.
- Play notes with the computer keyboard out of the box. Requiring a MIDI
  controller would lose most of the target users in the first thirty seconds.
- Ship 40 or so factory presets organized by vibe, not by synthesis type.
  "Warm pad," not "2-osc LP24 pad."
- Every preset is a starting point, not an endpoint. Put the text box right
  there in the preset browser: "load this, then describe what to change."

| # | Deliverable | Done when |
| --- | --- | --- |
| M0 | Scaffold, schema, codegen, test harness, CLAUDE.md | CI green on an empty engine |
| M1 | One sine voice to the speakers | Note on and off with zero clicks, passes silence and DC tests |
| M2 | Full subtractive voice, 16 note polyphony | Passes the aliasing test, voice stealing is inaudible |
| M3 | Effects chain and mod matrix | Golden renders locked in |
| M4 | Full UI bound to real engine, presets save and load | A stranger can make a sound without instructions |
| M5 | Natural language control | "Make it darker and wider" does the right thing, and you can see it happen |
| M6 | Audio match, tiers 1 and 2 | A supersaw reference gets a recognizable match in under 90 seconds |
| M7 | Tauri packaging, onboarding, 40 factory presets | Someone else installs it and gets a sound in under 2 minutes |

M0 through M4 is a real, useful, shippable synthesizer. Treat that as the
actual project and M5 through M7 as the reason it is interesting.

## 11. Addendum: the DAW control track

A second idea in circulation is an MCP that drives Ableton or Logic for the
user. Three things to know before spending time on it.

**Ableton is already well covered.** There are at least half a dozen working
MCP servers for Live. They split into two approaches: a Remote Script that
opens a socket and speaks JSON (ahujasid/ableton-mcp), or a bridge over
AbletonOSC (Simon-Kansara/ableton-live-mcp-server, and others). Between them
you get track and clip creation, device loading from Live's browser,
transport and tempo control, MIDI note insertion, and mixer parameters.
Building another one is not a differentiated project. Installing one and
using it is worth an hour.

**Logic is basically not scriptable in the same way.** Scripter is a MIDI FX
plugin running JavaScript in a sandbox on a single track. It processes MIDI
passing through that channel strip and nothing else. No imports, no file I/O,
no access to the project structure, tracks, mixer, or arrangement. You cannot
build a Logic equivalent of the Ableton MCP without resorting to UI
scripting, which is fragile and breaks on every point release. If DAW control
matters, the answer is Ableton.

**Building your own DAW is a much larger project than the synth.** Timeline,
arrangement, audio engine, plugin hosting, latency compensation, undo across
a document model. That is years, not weekends. Do not let it into scope.

**The move that connects both ideas.** Once the engine exists, wrap it two
ways from the same core: (1) the standalone Tauri app, which is the beginner
product described above; (2) a CLAP and VST3 plugin via nih-plug, so it loads
in Ableton, FL, Bitwig, and Logic like any other instrument. Then expose the
synth's own MCP server, so an agent can drive this instrument inside someone
else's session: "load Synthonos on track 3, make a wide detuned supersaw,
write an eight bar chord progression." The existing Ableton MCP handles the
session; ours handles the sound design. Those compose rather than compete.
This is the strongest argument for keeping the DSP layer dependency-free and
portable to Rust from day one. The plugin build is the thing that makes the
DAW integration possible, and retrofitting it later means a rewrite.

**On the Nexus interface as a reference.** Worth studying closely, for one
thing it does right and one it does wrong. Right: the entire center of the
plugin is a preset browser, not a synthesis panel. Nexus is preset-first by
design. That is the same instinct behind putting the text box at the top of
this layout; most users arrive wanting a sound, not a signal path. Wrong, for
this audience: the controls around the edge are small, unlabeled except for
three-letter abbreviations (atk, dec, sus, rel, res, spread, det), grouped by
engineering function rather than by result. Someone with no synth experience
learns nothing from looking at it. Keep the density and the craft of that
look. Replace the abbreviations with real words, and let hovering explain
what a control does in a sentence a musician would use.
